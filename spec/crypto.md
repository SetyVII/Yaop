# Crypto contract — vault E2EE

How everything that leaves a YAOP device is generated, derived, wrapped and encrypted. It is law
for the three platforms; the reference implementation lives in `server/internal/simclient/` (Go)
and the fixtures with exact vectors in `spec/fixtures/crypto/`. The end user sees none of this
except the 24-word phrase.

Principle (product §15.1): the server never receives anything readable. If an optimization needs
plaintext on the server, it is dropped.

## Vault Key (VK)

- The **VK** is 32 random bytes (256 bits), generated by `crypto/rand` (or the OS generator) on
  the first device.
- The VK is identified by its epoch: each rotation (revoking a device, product §15.3) increments
  `key_epoch` (u32, starting at 1) and yields a new VK; every encrypted blob declares its epoch
  in the envelope.
- Local storage: the VK is wrapped by the system keystore (Android Keystore; Secret Service on
  Linux, or a passphrase-wrapped file when there is no keychain).

## BIP39: the recovery phrase

The 24-word phrase **is** the VK: the 32 bytes of entropy of the BIP-0039 standard (official
English list, standard SHA-256 checksum, 256 bits → 24 words). There is no passphrase:
`PBKDF2-HMAC-SHA512(mnemonic, salt="mnemonic", 2048 iter, 64 bytes)` exists for compatibility
with the standard, but the vault **does not use the seed as key material: the VK is the entropy
itself**.

- `entropy → mnemonic`: 256 bits of entropy + 8 checksum bits (first byte of SHA-256 of the
  entropy) = 264 bits = 24 indices of 11 bits over the wordlist.
- `mnemonic → entropy`: split by spaces (exactly 24 words), each word must exist in the list
  (byte-exact match; the list is ASCII), rebuild the bits and validate the checksum; a bad
  checksum or an unknown word → error, never "best effort".
- The official wordlist (2048 words) is in the repo: `spec/fixtures/crypto/bip39_english.txt`
  (sha256 `2f5eed53a4727b4bf8880d8f3f199efc90e58503646d9ff8eff3a2ed3b24dbda`); the three
  platforms load it (embedded in the build, never downloaded).
- Vectors: the official BIP-0039 ones (entropy `00…00` → `abandon … art`, etc.) and the invalid
  cases in `spec/fixtures/crypto/bip39.json`.

Recovery contract: **without the phrase and without a device holding the VK, the data is
unrecoverable**, and the app says so during onboarding (product §15.2).

## Subkeys per domain (HKDF)

```
subkey(dom) = HKDF-SHA256(ikm = VK_epoch, salt = "yaop-vault/1", info = "<domain>")  // 32 bytes
```

- `salt` is the ASCII literal `yaop-vault/1`; `info` is the ASCII domain name. Output is always
  32 bytes.
- Domains: `objects`, `ops`, `snapshots`, `assets`, `thumbs`, `derived`, `ids`.
- Each payload type is encrypted with its own subkey: a compromise in one domain does not cross
  to the others. The `ids` subkey does not encrypt: it is a MAC key (see "Blind ids").
- Exact vectors (fixed test VK → 7 hex subkeys): `spec/fixtures/crypto/hkdf_domains.json`. A
  change in salt/info/length breaks ALL platforms: exact hex, not approximate.

## AEAD: XChaCha20-Poly1305

- Construction: `subkey = HChaCha20(key, nonce[0:16])`; then ChaCha20-Poly1305 (RFC 8439) with
  `key=subkey` and the 12-byte nonce `0x00000000 || nonce[16:24]`. It is
  `AEAD_XCHACHA20_POLY1305` from draft-irtf-cfrg-xchacha-03.
- The key is ALWAYS a domain subkey (never the VK itself, never a passphrase).
- The nonce is **24 random bytes per envelope** (no counter: 192 bits make collisions
  negligible). Reusing a nonce with the same key breaks Poly1305: generation is always
  `crypto/rand`.
- The AAD authenticates the exact context of each blob: see "Envelope" and "Blind ids".
- Exact vectors: the official one from the draft §A.1 (key `80…9f`, nonce `40…57`, AAD
  `50515253c0c1c2c3c4c5c6c7`, text "Ladies and Gentlemen…" → exact ciphertext+tag) and the
  HChaCha20 one from §2.2.1, in `spec/fixtures/crypto/aead_xchacha20poly1305.json`. The runner
  also checks that one changed byte in ct/tag/AAD/key makes authentication fail.

## Blind ids (wire_id)

The server must not see meaningful ids (`daily-2026-11-09`, `tag_my_topic`, `media_<asset>`,
product §15.1). On the wire travels:

```
wire_id = hex(HMAC-SHA256(key = subkey "ids", msg = real_id_utf8))[0:32]
```

- The **first 16 bytes** of the HMAC, in **lowercase hex** (32 ASCII chars).
- Deterministic: two offline devices creating the same day's note produce the same `wire_id`,
  and the merge reconciles them anyway.
- The `ids` subkey belongs to the SAME epoch as the rest: rotating the VK rotates the wire_ids
  and the client re-blinds.
- **Composite ids** (`derived/…`, product §23.3): the HMAC input is the full composite id
  `derived/<objectId>/<kind>`, so neither the object nor the kind is visible to the server.

Vectors: `spec/fixtures/crypto/wire_id.json` (daily/tag/media + 2 different kinds of the same
derived object).

## The envelope

Every blob (operation, object, snapshot, chunk, derived artifact, VK during pairing) travels as:

```
version(1 byte) | key_epoch(4 bytes, big endian) | nonce(24 bytes) | ciphertext+tag
```

- **Version `0x01`**: the payload inside is the data as-is (uncompressed). **ALWAYS valid** in
  any domain.
- **Version `0x02`**: the payload was **compressed with zstd (production level 3) BEFORE
  encrypting**. The producer decides; the consumer accepts both versions.
  - In production, the **JSON** payloads of kinds `obj|type|asset_meta|derived|snapshot` use
    `0x02`; media chunks (binary, already compressed) use `0x01`.
  - zstd is not byte-deterministic across versions/libraries: **the bytes of a 0x02 envelope
    are never compared**; its fixture checks the round trip (`envelope_zstd_roundtrip.json`).
  - Forging the version does not help: a `0x02` envelope whose payload is not a zstd frame fails
    zstd's magic number, and a `0x01` with a zstd frame inside fails protocol parsing; both fail
    closed.
- The **AAD authenticates the exact identity of the blob**: `"<domain>/<wire_id>"`, and for
  asset chunks `"assets/<wire_id>/chunk/<n>"` with `n` in decimal ASCII without padding.
- `key_epoch` is in clear (the server needs it to order epochs) but **protected**: opening with
  another epoch's subkey fails authentication.
- Exact vectors (v1, fixed nonces, full envelope bytes) in `spec/fixtures/crypto/envelope.json`.

## Pairing a new device (QR + X25519)

An enrolled device (A) adds another (B) without the VK ever travelling in clear (product §15.3):

1. **A generates an ephemeral X25519 pair** `(a, A_pub)` and shows the QR.
2. **The QR contains exactly** this JSON (UTF-8, compact, keys in this order):

   ```json
   {"v":1,"server_url":"https://…","tls_fp":"<sha256-hex-32B>","eph_pub":"<base64url-no-padding 32B>","pairing_id":"<hex 32 chars = 16B>"}
   ```

   - `v` = 1. `server_url` = server URL. `tls_fp` = lowercase hex SHA-256 of the SPKI (DER) of
     the server's TLS certificate: the new device checks nobody is impersonating it. `eph_pub` =
     A's ephemeral public key. `pairing_id` = 16 random bytes in hex (32 chars) identifying the
     transaction.
3. **B scans and generates its own ephemeral pair** `(b, B_pub)` and sends `B_pub` to A through
   the server (pairing endpoints in `server/README.md`).
4. **Both derive the secret**: `shared = X25519(own_priv, other_pub)` (32 bytes, never leaves
   the pair).
5. **Short code**: both show 6 digits for the human to compare.

   ```
   code = zero-pad-6( big-endian-u32( HKDF-SHA256(shared, salt="yaop-pairing/1", info="short-code")[0:4] ) mod 10^6 )
   ```

6. **A wraps the VK** with the transfer key

   ```
   vk_key = HKDF-SHA256(shared, salt="yaop-pairing/1", info="vk-transfer")  // 32 bytes
   ```

   in a version `0x01` envelope, `key_epoch` = the vault's current epoch, a random 24-byte nonce
   and AAD `"pairing/<pairing_id>"`; the payload is the VK (32 bytes). B opens it, checks the
   code matches its own and is enrolled.

The full transcript with fixed test keys (every intermediate value in hex) is
`spec/fixtures/crypto/pairing_transcript.json`; the runner replays it step by step and reproduces
the exact bytes.

## Rotation

Revoking a device (product §15.3): the server invalidates its token; the vault moves to
`key_epoch+1` with a new VK (chosen by the revoking device); new data is encrypted with the new
subkeys from then on; old blobs are re-encrypted in the background (trusted node, product §23).
A revoked device decrypts nothing new: its keys only serve past epochs.

> **Status: proposed design, not implemented (see ROADMAP.md).** The paragraph above is the
> product decision; what follows is how to achieve it.

### The problem

The new VK must reach the devices that **stay** without the revoked one reading it. Wrapping it
with the old VK does not work (the revoked device knows it) and the server must not see it.
Today a device has no cryptographic identity of its own: pairing uses ephemeral X25519 keys.

### Proposed design

1. **Device key.** Each device generates an X25519 pair when paired (private key in the
   Keystore/keychain, never leaves) and registers the **public** key in its server record
   (`enroll` / `/v1/devices`). The server can see it without harm (it is not content).
2. **Key ring.** The client keeps `{epoch → VK}` instead of a single VK, because old blobs stay
   encrypted with their epoch. Opening an envelope picks the key by `key_epoch`; sealing always
   uses the newest.
3. **`key_rotation` operation** (new kind, no domain: structurally signed, not encrypted with the
   VK). Payload: `{ "v":1, "new_epoch":N, "revoked":"dev_x", "wraps": { "<device_id>": "<X25519+HKDF
   envelope of the new VK>" … } }`. Each `wrap` uses the same construction as pairing
   (`sealPairingVk`) with the recipient's public key. The server checks that the revoked device
   has no wrap and that `new_epoch = current_epoch+1` (it cannot decide the content).
4. **Apply** (a client receiving `key_rotation` with a wrap for it): opens its wrap, adds the VK
   to the ring, moves to `new_epoch` and rewrites its local blobs as needed. A client without a
   wrap (the revoked one) cannot advance.
5. **Deferred re-encryption** (trusted node): old objects and assets are re-emitted under
   `new_epoch` in the background; meanwhile the ring reads both.
6. **Tests**: fixture `spec/fixtures/crypto/rotation.json` (old and new VK, two devices, one
   wrap per recipient, the revoked one without) and a server test "the revoked device cannot
   decrypt new operations".

### Decisions this design implies

- The server stores each device's **public key** (not content).
- Any authorized device can revoke (product §15.3), not only the first one.
- A device offline during the rotation gets its wrap when it comes back (the wrap stays in the
  log).

## `.yaop` backup (product §15.6)

A single file, encrypted with the VK, restored **with the phrase alone** and no server.

```
file    := "YBK1" | record*
record  := length(u32 BE) | envelope            (envelope = the one above)
```

- Each envelope uses the `snapshots` domain subkey and `AAD = "snapshots/backup/<i>"`, with
  `i` = the record index (0, 1, 2…) in decimal. The index in the AAD prevents reordering or
  removing records.
- Payload of each record (before encryption):
  `type(1) | idLen(u16 BE) | id(utf-8) | n(u32 BE) | total(u32 BE) | data`.

| type | meaning | `id` | `n` / `total` | `data` |
|---|---|---|---|---|
| `0x01` | object | real id | 0 / 0 | full wire JSON of the object (same as an `obj` op) |
| `0x02` | object type | type id | 0 / 0 | wire JSON of the type |
| `0x03` | asset piece | asset id (without `media_`) | 0-based index / number of pieces | plaintext bytes, at most 4 MiB per piece |
| `0xFF` | end | empty | number of previous records / 0 | empty |

- JSON records (`0x01`, `0x02`) may use a `0x02` envelope (zstd); pieces and the end record use
  `0x01`. The reader accepts both.
- A file without the `0xFF` record, with trailing bytes, or with a different count **is
  rejected** (truncated or tampered).
- Restoring = treating each object/type as a remote op (`merge(local, remote)`, idempotent) and
  reassembling assets by `id`; restoring twice, or over a vault with data, never loses anything.
- The backup is encrypted with the VK of the `key_epoch` current at export; the vault phrase
  opens it.
- Fixture: `spec/fixtures/backup/small.yaop` (exact bytes, fixed nonces `0x20+i`, no zstd) and
  `small.json` (VK, epoch and expected records). Each platform must (1) open it and get exactly
  those records, (2) write the same file byte for byte with the same nonces, (3) reject the
  negatives (wrong VK, truncated, one byte changed, bad magic, record removed).

### Importing a Facultas backup

YAOP grew from Facultas. A `.facultas` backup is the same container with magic `"FBK1"` and HKDF
salt `"facultas-vault/1"` for its subkeys; the VK is the same 24-word entropy. Restore accepts it
(read only, chosen by the magic) so a vault moves over with its phrase: create the YAOP vault
with "restore with my phrase", then restore the `.facultas` file. YAOP never writes `FBK1`.
Fixture: `spec/fixtures/backup/legacy-small.facultas` (the records of `small.json`).
Implemented on desktop; Android and `simclient` do not read it yet.

## Libraries per platform

All must pass the same vectors in `spec/fixtures/crypto` (the conformance suite requires it).

| Platform | AEAD XChaCha20-Poly1305 | HKDF-SHA256 | X25519 | HMAC/SHA-2 (wire_id) | BIP39 | zstd |
|---|---|---|---|---|---|---|
| **Go (reference, `simclient`)** | `golang.org/x/crypto/chacha20poly1305` (`NewX`) | `golang.org/x/crypto/hkdf` | `golang.org/x/crypto/curve25519` | stdlib `crypto/hmac`, `crypto/sha256` | by hand (SHA-256 checksum + `x/crypto/pbkdf2`; wordlist from `spec/fixtures/crypto/`) | `github.com/klauspost/compress/zstd` |
| **Kotlin (mobile)** | **BouncyCastle `bcprov-jdk18on`**: `ChaCha20Poly1305` + `XChaCha20` (or HChaCha20 by hand: HChaCha20 subkey + 4 NUL + nonce[16:24]) | `HKDFBytesGenerator` + `SHA256Digest` | `org.bouncycastle.math.ec.rfc7748.X25519` | stdlib `javax.crypto.Mac` HmacSHA256 + `MessageDigest` | by hand (like Go, same wordlist) | `com.github.luben:zstd-jni` |
| **C++ (pkmcore)** | **libsodium**: `crypto_aead_xchacha20poly1305_ietf_*` | by hand over `crypto_auth_hmacsha256` (libsodium has no HKDF-SHA256) | `crypto_scalarmult_curve25519` | `crypto_auth_hmacsha256` | by hand (like Go) | system **libzstd** (`ZSTD_compress`/`ZSTD_decompress`, level 3) |

Notes:

- **Not Tink** on Android: it does not expose X25519 nor allow fixing HKDF parameters in a stable
  way; BouncyCastle implements the needed primitives.
- BIP39 is shared in practice because the wordlist is a repo file and PBKDF2-SHA512 exists on
  all three platforms.

## What this contract does NOT allow

- A passphrase/Argon2id for the vault (rejected, product §15.2). The phrase IS the key.
- A server that sees titles, types, MIME types, file names, dates or the graph (product §15.1).
  Everything leaves inside an envelope.
- Deriving subkeys with another salt, info or length: the vectors are exact.
- An "unencrypted local mode": the local DB is always encrypted (SQLCipher on both clients,
  product §15.5).
